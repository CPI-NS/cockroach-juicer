# Experiment workflow

Before planning, running or analyzing experiments, read [bench/README.md](bench/README.md) and its capability references. Use `python -m crdb_bench` for the supported SQL YCSBT scope; keep ordinary runs configuration-only, with explicit inventory, workload and pinned artifacts. Preserve historical scripts/data; maintain adapter fixes in `bench/` and reusable runtime fixes in the experiment-common repository.

For installation or a fresh checkout, read [pinned package installation](bench/packaging/README.md). Verify the common artifact against `bench/packaging/common-pin.json` and `bench/uv.lock`; use the selected environment's interpreter. Standalone execution requires experiment-common and this adapter, with no juicer-project checkout dependency. For AWS, read the installed `share/experiment-common/docs/infra.md`, or `docs/infra.md` in your experiment-common checkout. Use `python -m experiment_common.infra`: all AWS provisioning, queries, release and audit belong to the initiating host. EC2 control performs build/deploy/run/collection through SSH only, without AWS credentials or an instance profile.

Establish continuous progress observation and verify worker deadline guards before load. Use public status/stop/collection operations; verify worker → control → durable results before normal release. Cleanup targets only owned processes and workers; retain control and protect unrelated resources. Report unsupported capabilities explicitly before execution.

Use the maintained `run-experiments` Skill, distributed from experiment-common, for experiment execution. Its references resolve templates and documentation from the selected installed environment, not a sibling checkout. Keep the Skill version with the run handoff. Legacy runners are archived evidence, not alternative launch paths.
